# galaxy-buds-multipoint

삼성 계정 없이, 컴퓨터에서 Galaxy Buds 멀티포인트 쓰기.

*[English](README.md)*

이런 순간, 아마 겪어 보셨을 거예요. Galaxy Buds2 Pro가 휴대폰과 노트북에 동시에
연결돼 있고 — 멀티포인트라는 게 원래 그러라고 있는 거니까요 — 노트북에서 재생을
누르는 순간 버즈가 조용히 휴대폰 연결을 끊어 버립니다.

찾아보면 설명은 대체로 하나로 모여요. 삼성이 "두 기기가 같은 삼성 계정에 로그인돼
있을 때"만 멀티포인트를 허용하는데, 컴퓨터는 그 조건을 만족할 방법이 없다는 거죠.
그럴듯하게 들리지만, 진단이 틀렸습니다.

펌웨어가 계정을 보는 건 맞아요. 다만 그 전에 먼저 검사하는 게 따로 있고, 컴퓨터는
바로 거기서 걸립니다. 계정 검사에는 도달조차 못 해요. 앞 단계에서 보는 건 버전 바이트
하나인데, 갤럭시 휴대폰이 페어링할 때 보내는 단 하나의 프로토콜 프레임으로 설정되고
서드파티 클라이언트는 아무도 보내지 않는 값입니다. 한 번만 보내 주면 멀티포인트가
제대로 동작해요. 휴대폰과 컴퓨터가 같이 연결되고, 계정은 처음부터 끝까지 등장하지
않습니다.

```bash
cd macos && ./budsmp apply
```

이게 전부예요. 프레임 하나, `fc0b00014304030400000b021eafcc`가 다입니다. 연결을 끊고
다시 붙어도 그대로 남지만, 버즈가 전원을 내리면 사라집니다. 그 바이트가 부팅 때 지워지는
RAM에 있기 때문이에요. 그래서 케이스에 한동안 넣어 뒀다면 멀티포인트가 다시 말을 안 들을
테고, `apply`를 한 번 더 실행하면 됩니다. 저희도 기대한 결과는 아니었어요. 어떻게 측정했고
왜 펌웨어 쪽에 우회로가 없는지는
[docs/experiments.md](docs/experiments.md#does-the-write-persist)에 적어 뒀습니다.
아예 되돌리고 싶으면 `./budsmp revert`로 원래 값 그대로 복구할 수 있어요.

## 지원 현황

| 플랫폼 | 상태 | 구현 |
|---|---|---|
| macOS 11+ | 동작 확인, 실제 기기에서 검증 | Swift + IOBluetooth, [macos/](macos/) |
| Linux | 구현 완료, 실제 기기 검증 전 | Python + `AF_BLUETOOTH`, [linux/](linux/) |
| Windows 10+ | 구현 완료, 실제 기기 검증 전 | Python + `AF_BTH`, [windows/](windows/) |

가운데 칸은 말 그대로의 의미예요. Linux와 Windows 도구는 macOS 쪽과 바이트 단위로
똑같은 프레임을 만들고, 실제 하드웨어에서 캡처한 프레임과 대조해서 확인했어요.
소켓·기기 탐색·리포트 경로에도 각각 테스트가 있고요. 다만 아직 아무도 진짜 버즈에
대고 돌려보지는 않았습니다. 먼저 시도해 보셨다면 결과를 알려 주시면 정말 좋겠어요.

전부 Galaxy Buds2 Pro에서 개발하고 확인했습니다. 원리 자체는 특정 모델에 묶여 있지
않아서 `SPPSERVICE4`를 광고하는 다른 Galaxy Buds에서도 똑같이 통할 것 같지만, 검증되지
않았어요 — 제보는 언제든 환영입니다.

## 무슨 일이 벌어지고 있나

두 번째 기기에서 오디오가 올라오면 버즈는 두 단계로 검사를 합니다.

**1단계 — `asVer` 게이트.** 버즈는 페어링된 기기마다 작은 레코드를 들고 있는데, 그중
1바이트가 `asVer`예요. 두 피어 중 하나라도 값이 `{2, 3}` 밖이면 버즈는 둘 중 하나의
연결을 끊습니다(이유 코드 `0xa9`). 컴퓨터가 끝내 통과하지 못하는 게 이 단계예요.

**2단계 — 계정 게이트.** 1단계를 통과해야만 도달합니다. 두 피어의 삼성 계정 해시를
비교하는데, 한쪽 피어가 "special"로 분류되면 비교를 아예 건너뛰어요. 컴퓨터가 바로 그
"special"에 해당합니다.

그러니까 다들 원인으로 지목하던 계정 검사는 애초에 문제가 아니었던 거예요. 컴퓨터가
거기서 떨어진 게 아니라, 거기까지 가지도 못했던 거죠.

`asVer`를 쓰는 메시지는 딱 하나, `SPPSERVICE4` RFCOMM 채널의 `MDE_VERSION`입니다.
갤럭시 휴대폰은 페어링 중에 이걸 보내요.
[GalaxyBudsClient](https://github.com/timschneeb/GalaxyBudsClient) 같은 서드파티
클라이언트는 *다른* 채널(`GEARMANAGER`)에 붙고 이 메시지를 보내지 않아서, `asVer`가
계속 `0`에 머물고 1단계에 계속 걸립니다.

그래서 해결책도 꽤 심심해요. 그 메시지 하나만 보내면 됩니다. 핸들러가 검사하는 건
`version <= 3` 하나뿐이고, 서명도 논스도 계정 비슷한 것도 필요 없어요.

계정 해시가 정말 필요 없다는 것도 추측이 아닙니다. 게이트가 실제로 살아 있다는 걸
보여 주는 양성 대조군까지 포함해서 실제 기기에서 확인했어요. 일부러 틀린 계정을 넣어도
휴대폰은 연결을 유지했고, 계정을 0으로 밀어도 유지했고, *올바른* 계정에 `asVer = 0`을
넣었을 때는 끊겼습니다. 방법과 결과는 [docs/experiments.md](docs/experiments.md)에
정리해 뒀어요.

더 깊이 들어가고 싶다면 와이어 포맷은 [docs/protocol.md](docs/protocol.md), 펌웨어
쪽은 [docs/firmware-gate.md](docs/firmware-gate.md)를 보시면 됩니다.

## 설치하고 실행하기

### macOS

```bash
git clone https://github.com/id6917824/galaxy-buds-multipoint
cd galaxy-buds-multipoint/macos
./build.sh
./budsmp apply
```

Xcode 커맨드 라인 도구(`xcode-select --install`) 말고는 필요한 게 없어요. 버즈를 먼저
연결하고, macOS가 블루투스 접근 권한을 물으면 **허용을 눌러 주세요** — 도구는 그 답을
기다리며 가만히 멈춰 있고, 이 대화상자는 다른 창 뒤에 숨는 버릇이 있습니다.

```bash
./budsmp read      # 이 호스트에 대해 버즈가 저장해 둔 값 보기
./budsmp revert    # 되돌리기
./budsmp --help    # 전체 명령과 옵션
```

`apply`가 채널을 열지 못하면 버즈가 자고 있는 거예요. 케이스에서 꺼내고, 오디오 출력
장치로 선택한 다음 아무거나 재생하고 다시 시도해 보세요. 나머지 실패 상황은
[macos/README.md](macos/README.md)에 정리해 뒀습니다.

### Linux

```bash
git clone https://github.com/id6917824/galaxy-buds-multipoint
cd galaxy-buds-multipoint/linux
./budsmp apply
```

Python 3.9 이상과 BlueZ가 필요한데, 데스크톱 Linux라면 거의 확실히 둘 다 이미 있을
거예요. 빌드할 것도 없습니다 — RFCOMM은 표준 라이브러리에서 그대로 가져와요.
`bluetoothctl`로 버즈를 먼저 페어링한 다음 [linux/README.md](linux/README.md)를
참고하시면 됩니다.

### Windows

```bat
git clone https://github.com/id6917824/galaxy-buds-multipoint
cd galaxy-buds-multipoint\windows
budsmp apply
```

Python 3.9 이상만 있으면 되고 그 외에는 아무것도 필요 없어요. 관리자 권한도, 빌드
과정도 없습니다. 설정에서 버즈를 먼저 페어링한 다음
[windows/README.md](windows/README.md)를 보세요.

### 프로토콜 도구만 쓰고 싶다면

프레임 빌더와 디코더는 Python 3만 돌아가면 어디서든 동작하고, 의존성도 없어요.

```bash
cd python
python3 -m budsmp.frame version-only 2                         # 픽스 프레임 생성
python3 -m budsmp.frame decode fc0b00014304030400000b021eafcc   # 프레임 분해
python3 -m budsmp.frame selftest                               # 캡처한 바이트와 대조
```

## 안전한가요?

낯선 사람 코드를 내 이어폰에 들이기 전에 당연히 물어볼 만한 질문이죠. 하는 일은 버즈가
이미 컴퓨터마다 들고 있는 레코드에서 1바이트짜리 필드 하나를 쓰는 것뿐이에요.
그러니까:

- **되돌릴 수 있어요.** `./budsmp revert`가 원래 값을 복원하고, 재페어링도 필요
  없습니다.
- **펌웨어를 건드리지 않아요.** 플래싱하는 게 없습니다. 버즈가 직접 광고하는 채널로
  보내는 평범한 프로토콜 메시지고, 휴대폰이 보낼 때와 똑같이 받아들여요.
- **아무 데도 전송하지 않아요.** 네트워크도, 계정도, 텔레메트리도 없습니다. 버즈와
  이야기하는 건 블루투스로 연결된 본인 컴퓨터뿐이에요.
- **해당 호스트에만 적용돼요.** 실행한 컴퓨터의 레코드만 건드리고, 휴대폰 레코드는
  그대로 둡니다.
- **영구적인 변경이 아니에요.** 버즈가 전원을 내릴 때 알아서 값을 지우고, 초기화해도
  지워집니다. 어느 쪽이든 다시 실행하면 됩니다.

반대로 하지 않는 일도 분명해요. 없는 기능을 해금하지 않고, 오디오 처리에 손대지 않고,
휴대폰 쪽은 아무것도 바꾸지 않습니다.

현실적으로 최악의 상황이라고 해 봐야 버즈가 한쪽 기기를 잠깐 끊는 정도인데, 그건 픽스
이전에 이미 하고 있던 동작이고 다음 쓰기로 되돌아갑니다.

## 한계

- **적용 상태가 유지되지 않아요.** 재연결은 괜찮지만, 버즈가 케이스에서 전원을 내린
  뒤에는 `apply`를 다시 실행해야 합니다. 호스트 쪽 우회로는 없습니다. 레코드가 부팅 때
  지워지는 RAM에 있고, 재연결할 때 레코드를 복원하는 루틴이 이 바이트만 일부러 건드리지
  않아요. 계정 해시는 복원하면서 `asVer`는 원래 값을 그대로 되쓰기만 합니다. 고정하려면
  펌웨어를 바꿔야 해요. 측정 결과와 주소는
  [docs/experiments.md](docs/experiments.md#does-the-write-persist)에 있습니다.
- 실행한 호스트만 고쳐져요. 컴퓨터가 두 대면 각각 한 번씩 실행해야 합니다.
- 버즈가 유지하는 활성 링크는 2개고, 이 픽스가 그 상한을 올려 주지는 않아요.
- 오디오는 실제로 재생 중인 기기를 따라갑니다. 쉬고 있는 기기에서 재생을 시작해도 다른
  쪽이 멈출 때까지는 스트림을 가져오지 않아요. 결함이 아니라 일반적인 멀티포인트 중재
  동작입니다.
- 버즈를 초기화하면 함께 초기화돼요.

## 면책

본인이 소유한 하드웨어를 그 하드웨어와의 상호운용을 위해 리버스 엔지니어링한
결과물이에요. 이미 손에 들고 있는 기기들이 제대로 함께 동작하도록 프로토콜 세부사항
하나를 문서화한 것이고, 삼성의 코드는 포함하지 않습니다.

본인 기기에 사용해 주세요. 삼성과 제휴·보증·지원 관계가 전혀 없고, 보증(워런티)이
무효가 될 수 있으며, 펌웨어 업데이트로 언제든 동작이 멈출 수 있습니다. 어떠한 보증도
없이 있는 그대로 제공됩니다 — [LICENSE](LICENSE)를 참고해 주세요.

"Galaxy Buds"와 "Samsung"은 삼성전자의 상표입니다.

## 기여

이런 제보가 특히 도움이 돼요.

- **Linux나 Windows 도구가 동작했나요?** 둘 다 구현은 끝났지만 실제 버즈로는 검증되지
  않았어요. "잘 됐다" 또는 "이 로그와 함께 실패했다" 한 줄이 지금으로선 가장 값진
  정보입니다.
- **다른 Galaxy Buds 모델.** `budsmp scan`에 `SPPSERVICE4`가 보이는지, `apply`가
  통하는지 알려 주세요. 모델명과 펌웨어 버전을 같이 적어 주시면 더 좋아요.

한 가지 부탁이 있어요. 로그를 올리기 전에 먼저 스크럽해 주세요. `budsmp` 출력에는
본인의 블루투스 주소가 들어 있고, `read`는 삼성 계정 해시를 그대로 출력합니다.
